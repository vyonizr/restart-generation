# Friends and friendly arenas (Reset Generation client) — RE notes

Windows `ResetGeneration-Win32-Web.dll` VAs unless marked **Mac** (`tr\mac_named.c`). "Observed" = read in code.
"Inferred" = my conclusion, not executed. Byte layouts reuse re_casino.md notation: `S` = String
(`u32 0, u32 n, u32 n, n bytes`), `P` = Profile (`u32 count, count x {S key, S value}`), `CI` = CasinoInfo
(`u8 type, u32 id, u32 inLobby, u32 waiting, u32 playing, S name`), `RB` = response base (`u8 result, u32 value`).
All integers little-endian. Example hex below was generated by `SCRATCH\fr_hex.js` (alice = id 2, bob = id 3,
friendly casino id 1001 = `e9 03 00 00`, name `alice`).

## 0. Summary for the server

1. **Two friend layers, one source of truth.** The Edit Friends menu, the "online" icon, and the
   CREATE_FRIENDLY_ARENA precondition all come from the **SNAP buddy list** (C=302 + events 307-311). The casino
   friend messages (REGISTER_FRIENDS, FRIEND_ADD/REMOVE, LOGIN/LOGOUT events) only tell the casino server who
   is a friend. The casino LOGIN/LOGOUT events have no visible UI effect that I found.
2. **The native code never calls `setPresence`.** Availability comes only from SNAP login (`P9=1`) and logout.
   The server must push event **307** itself, after the client has fetched its buddy list.
3. **A friendly casino = CasinoInfo type 2, unique id (not 1), name = host's profile `name`.** Clients find
   friendly casinos by name, hide the one whose name equals their own name, and show it as
   "SPACE_FOR_X_AND_FRIENDS" with X = name.
4. **Friendly flow = ranked flow on MT type 0x13.** ENTER, MATCHMAKING (with heroType/random), lobby list from
   MATCHMAKING events, then LOCK (0x11) + MATCHED_UP (0x13) + the same table/battle flow. The only friendly-only
   messages are CASINO_CREATE, FRIENDLY_CASINO_START, the friendly list/update/entered/left messages.
5. **Any lobby member can press START**, not only the creator (no host check in FUN_100eadd0).

### 1.2 State values (Java `Friend.getState`, used verbatim natively)
| int | Java STATE | Produced by | Edit Friends menu (Windows FUN_100e3bd0, Mac FUN_0007ebe8) |
|---|---|---|---|
| 0 | NONE | 307 with an availability string other than the three below | no case in the switch: builds a NULL component (crash risk, §4) |
| 1 | UNCONFIRMED | 302 status `from`; 308 | buttons ACCEPT / REJECT (`ACCEPT_<name>`, `REJECT_<name>`); arena menu highlights MANAGE_FRIENDS (FUN_100d8a10 -> FUN_100d8490) |
| 2 | REQUESTED | 302 status `to` | button CANCELREQUEST (`CANCEL_REQUEST_<name>`, does nothing) |
| 3 | ONLINE | 307 `available` | button REMOVE; state index passed to the item's icon (`FUN_100ff4f0(item+0xcc, state)`) |
| 4 | AWAY | 307 `away` | same as 3 |
| 5 | OFFLINE | 302 any other status; 307 `unavailable`; 309 accepted | same as 3 |

So **"online" in the menu = native state 3 = SNAP 307 `availability=available`.** The casino LOGIN event does not
touch the buddy state.

### 1.3 onPresence (FUN_10096610, observed)
- Buddy exists: if its state is 1 or 2, keep it; else `state = new state`. The presence string is ignored.
- Buddy unknown: keep a side list of online names (dispatcher+0x10): add the name if state == 3, else remove it.
  The list is applied by the next friend list (1.4) and then cleared.

### 1.4 onFriendList (FUN_10096b70, observed)
1. Delete every buddy whose state != 1 (pending incoming requests survive).
2. Add each listed name not already present, with state 3 if it is in the online side list, else the listed state.
3. Clear the side list. Call FUN_10096a50 = **send REGISTER_FRIENDS**.

Java side (`SNAPMobileClient.cacheBuddyList`): purges its cache and builds every entry as OFFLINE (5), `to` -> 2,
`from` -> 1. **C=302 never yields ONLINE.**

Consequence (inferred race): a 307 that the Java event queue delivers *before* the `SMEventFriendList` is lost
for buddies the native already knew (step 1 recreates them as 5). Push the 307s about 1 s **after** the C=302
reply.

### 1.5 When the client asks for the list
Only once: login-menu listener FUN_100c6380 (on CasinoSystem LOGIN response, first login) calls presence
`+0x20` = bridge 10109fb0 = Java `getFriendList` -> **C=302**, then opens the arena menu 7.5 s later
(`+0x58 = now + 0x1d4c`). After a battle the client re-logs into CasinoSystem without asking again.

### 1.7 What the SNAP server must send (byte-exact text)
- C=302 reply rows (`r.java aE`: `id|name|status`): `200 OK\n3|bob|both\n4|carol|to\n5|dave|from\n`
  (`to` = I asked them, `from` = they asked me, anything else = accepted).
- After that (≈1 s later), one 307 per **online accepted** buddy (field list `r.java` id 307; only fromID,
  fromName, availability, presence are read):
  `307|3|bob|available|42713|3|1|0|0|0|0|0|`  — availability must be exactly `available`, `unavailable` or `away`.
- On SNAP login (C=1, `P9=1`): push `307|<id>|<name>|available|...` to that user's online accepted buddies. On
  logout or session drop: same with `unavailable`. C=305 never arrives from this client.
- C=306 requestBuddy(P1 target): push to target `308|<fromId>|<fromName>|` (message base64, may be empty).
- C=307 accept(P1 requester): push to requester `309|<id>|<name>|1|`, then `307 ... available` both ways if online.
- C=308 decline(P1 requester): push to requester `309|<id>|<name>|0|`.
- C=309 remove(P1 other): push to other `310|<id>|<name>`.
- Event fields are split on `|`, `,` and `\n` (r.java line 133); keep names free of those.

## 2. Casino friend messages (0x11)

### 2.1 REGISTER_FRIENDS (client -> server)
`00 21 | u8 n | n x S name` (FUN_10095bc0 / writer FUN_10095d00), sent by FUN_10096a50 through
FUN_10046e90 after every native friend list (1.4). Contents: lower-cased names of all buddies with state != 1
(so pending **outgoing** requests (2) are included; pending incoming (1) are not).
**Reply: none.** Response 0x21 is in the ignore list of FUN_10047460. Treat the list as a hint; use the SNAP
accepted-buddy relation as truth.

### 2.2 FRIEND_ADD / FRIEND_REMOVE (client -> server)
`00 24 S name` sent by FUN_10096470 when the user presses ACCEPT; `00 23 S name` by FUN_10096950 on REMOVE.
Not sent when the *other* side accepts. **Reply: none needed.** If you reply to FRIEND_REMOVE
(`01 23 RB CI`), the client looks the CI name up (FUN_10094c50) and removes that friendly casino; the CI must be
type 1 or 2 (NULL deref otherwise) and its name must not equal the public casino name (§4).

### 2.3 Friend online/offline events (server -> client, 0x11) — optional
- LOGIN event `02 00 S subject P profile` (FUN_10098a00): creates a remote CasinoUser, stores it in the
  CasinoSystem online map (+0x10, FUN_100952b0 keyed by `id`), calls listeners `+4`.
  Example: `02 00 00 00 00 00 01 00 00 00 01 00 00 00 33 02 00 00 00 00 00 00 00 02 00 00 00 02 00 00 00 69 64 00 00 00 00 01 00 00 00 01 00 00 00 33 00 00 00 00 04 00 00 00 04 00 00 00 6e 61 6d 65 00 00 00 00 03 00 00 00 03 00 00 00 62 6f 62`
  Profile keys **`id` (decimal) and `name` are mandatory** (FUN_10047240 / FUN_100472c0 dereference the map hit
  without a NULL check).
- LOGOUT event `02 01 S id` (decimal id; FUN_100f2360 atoi): listeners `+8(id,0)`, removes the map entry
  (FUN_100950e0, safe for unknown ids). Example: `02 01 00 00 00 00 01 00 00 00 01 00 00 00 33`.
- Effect: the arena menu's listener slots +4/+8 are no-ops (10042fc0, 1009a7e0). The map lookups
  (CasinoSystem vtable 1017af90 +0xc FUN_10095340 by name, +0x10 FUN_10094da0 by id) have no external caller.
  Sending them is faithful but changes nothing visible.

## 3. Friendly arena happy path (2-4 players)

Channels: 0x11 = CasinoSystem (FUN_10047460 responses, FUN_10047bf0 events); 0x13 = friendly casino object
(FUN_100980a0 responses, FUN_100982b0 events). A casino registers its channel on enter (FUN_10097ff0: unregister
then register `casino+0x34`, which FUN_10097be0 sets to 0x12 for type 1, 0x13 for type 2). Only one friendly
casino can listen on 0x13 at a time.

### 3.1 Create (host alice)
Precondition (FUN_100d8aa0 `CREATE_FRIENDLY_ARENA`): FUN_1009a7d0 (always 1) **and** native buddy count != 0
(FUN_100961e0, any state, even a pending request). Else dialog `NO_FRIENDS`.
1. Client: `00 14 00 00 00 00` on 0x11 (FUN_10046a80).
2. Server -> host, 0x11: `01 14 RB CI(type 2)`:
   `01 14 00 00 00 00 00 02 e9 03 00 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65`
   Client (case 0x14): finds casino by id (FUN_10094bf0, checks the public casino first), else creates it
   (FUN_10097be0) and adds it (FUN_10094b60: type 2 -> friendly list; **type 1 would replace the public
   casino**). Listeners `+0x10(id)` -> arena FUN_100d83f0: `player->enterCasino(findById(id))` and opens the hero
   menu (FUN_100e33a0).
   - id: unique, never 1 (public id), positive (menu parses it with atoi).
   - name: host's profile `name`, exactly. inLobby: 1 (the host is about to enter; see 3.4 removal rule).
3. Client (auto): CASINO_ENTER `00 08 e9 03 00 00` on **0x13** (FUN_10097ff0; requires player state < 8).
4. Server -> host, 0x13: `01 08 RB P self CI`. Same layout as ranked; the client copies CI inLobby/waiting into
   its casino and goes to state 9 (ENTERED_CASINO). Profile must carry `id`, `name`, `fameLevel`:
   `01 08 00 00 00 00 00 04 00 00 00 00 00 00 00 02 00 00 00 02 00 00 00 69 64 00 00 00 00 01 00 00 00 01 00 00 00 32 00 00 00 00 04 00 00 00 04 00 00 00 6e 61 6d 65 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65 00 00 00 00 04 00 00 00 04 00 00 00 66 61 6d 65 00 00 00 00 01 00 00 00 01 00 00 00 30 00 00 00 00 09 00 00 00 09 00 00 00 66 61 6d 65 4c 65 76 65 6c 00 00 00 00 01 00 00 00 01 00 00 00 31 02 e9 03 00 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65`
5. Server -> each online accepted friend of alice, 0x11: FRIENDLY_CASINO_ENTERED `02 15 S subject CI S casinoName`
   (parser FUN_10098780: subject, CI via factory, String):
   `02 15 00 00 00 00 01 00 00 00 01 00 00 00 32 02 e9 03 00 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65`
   Client (FUN_10047bf0 case 0x15): looks the casino up **by the trailing name** (FUN_10094c50); if absent
   creates it from CI. If present, the new CI is discarded (id is *not* updated). Listeners `+0x24(casino, name)`
   -> arena FUN_100da310 -> FUN_100d97b0 adds menu entry `FRIEND_<id>` with text SPACE_FOR_X_AND_FRIENDS(name)
   and PLAYERS_IN_LOBBY = inLobby+playing, WAITING, PLAYING; skipped if name == own profile name.
   The subject string is not read (use the creator id).

### 3.2 Discovery by friends (three paths, all observed)
- **Push:** FRIENDLY_CASINO_ENTERED (above).
- **Pull on every arena-menu entry:** FUN_100d8a10 sends `00 07 00 00 00 00` (GET_FRIENDLY_CASINO_LIST).
  Response action 7 is ignored; reply with **F_CASINO (action 3)** on 0x11: `01 03 RB u8 n n x CI`
  (FUN_10097770/FUN_10097690). Client (case 3) **deletes all friendly casinos**, recreates them from the list,
  then listeners `+0x1c` -> arena FUN_100da290 rebuilds every `FRIEND_<id>` entry.
  One arena: `01 03 00 00 00 00 00 01 02 e9 03 00 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65`
  None: `01 03 00 00 00 00 00 00`. Send only as this reply (it frees casino objects a player could be in).
  List the open friendly casinos of the requester's accepted friends (exclude ones that already started).
- **Poll:** arena tick FUN_100d8700 -> FUN_100d85b0 every 6000 ms while buddies != 0 and friendly list != 0;
  lobby enter FUN_100ec1e0 and lobby ENTER events (FUN_100eafc0) also poll. Request per casino (FUN_10048120):
  `00 19 u32 casinoId` on 0x11. Reply `01 19 RB u32 id u32 inLobby u32 waiting u32 playing` (FUN_10096f20):
  `01 19 00 00 00 00 00 e9 03 00 00 02 00 00 00 01 00 00 00 00 00 00 00`
  Client sets the counts (CI vtable 101828b0 +0x38/+0x3c/+0x40) and **removes the casino if inLobby+playing == 0**
  (then unregisters 0x13 if the list is empty). Listeners `+0x18(id)` refresh the menu text (FUN_100da350).
  For a closed or unknown id reply with zeros: `01 19 00 00 00 00 00 e9 03 00 00 00 00 00 00 00 00 00 00 00 00 00 00`.

### 3.4 Hero pick and the friendly lobby (all members, host included)
- Hero menu FUN_100e3670 waits for player state 9, sets profile `heroType` and `random` (`TRUE`/`FALSE`), calls
  `player->startMatchmaking` -> **CASINO_MATCHMAKING `00 09 S heroType S random` on 0x13** (FUN_10097dc0), then
  creates ArenaLobbyState (FUN_100eb540). So yes, members send MATCHMAKING in a friendly casino.
- Lobby enter FUN_100ec1e0: `+0x5d = (casino type == 2)`; friendly -> sends FRIENDLY_UPDATE once.
- **Player list source (lobby+0x3c, count +0x34):** ICasino listener vtable 101894b8 slot +0xc FUN_100ebd00
  (add, dedup by name) fed by MATCHMAKING event (FUN_100982b0 case 9, skips own id) and MATCHMAKING response
  (FUN_100980a0 case 9, skips own id); slot +0x10 FUN_100ebe10 (remove by id) fed by CANCEL_MATCHMAKING event.
  ENTER/EXIT events only change the counter.

### 3.5 Start
Lobby input FUN_100eadd0 key 4: requires `+0x5d` (friendly), `+0x34 != 0` (at least one *other* member in the
list) and not already starting (`+0x5c`). It sends **FRIENDLY_CASINO_START `00 1c u32 casinoId` on 0x11**
(FUN_10046e00) and locks locally (listener +0x1c -> FUN_100ebeb0: player +0x90, +0x5c = 1, "GAME_STARTING").
Any member who sees another listed player can press it.

Server, on `00 1c e9 03 00 00`:
1. Ready set = members who sent MATCHMAKING (they are in ArenaLobbyState). Members still in the hero menu are
   not in a lobby: a SEAT_TAKE response would reach no JoinState (FUN_100ead20 is lobby-only), so leave them out.
2. If fewer than 2 ready or no battle template for n seats: reply `01 1c 01 00 00 00 00` (0x11). Client case 0x1c:
   result != 0 -> `player->+0x88` unlock -> lobby FUN_100eb070 MATCHMAKING_FAILED dialog. (Result 0 is ignored, so
   a success reply `01 1c 00 00 00 00 00` is optional.)
3. Else, for each ready member, in this order:
   - 0x11: LOCK_PLAYER_IN_GAME `00 1d 00 00 00 00` (non-starters show GAME_STARTING and can't cancel; harmless for
     the starter). Client answers `01 1d 00 00 00 00 00`.
   - 0x13: CASINO_MATCHED_UP `02 1f S subject TD` — identical to ranked (FUN_100982b0 case 0x1f is shared), with
     `maxplrs = n`. The client then disconnects the CasinoSystem session, joins `TD.name`, sends SEAT_TAKE on
     0x15; the rest is the ranked battle flow (re_match.md §3).
4. Send FRIENDLY_CASINO_LEFT (3.6) to friends outside the casino, or report `inLobby=0, playing=n` in polls, so
   nobody tries to join a started arena.
What non-starters see: hero/lobby screen with the list of matchmaking members and "WAITING_FOR_PLAYERS", then
"GAME_STARTING" on LOCK, then the battle. Without LOCK they still start, only the label differs.

### 3.6 Leaving and closing
- Lobby key 5 (if not locked): `00 0a 00 00 00 00` on 0x13; client sets state 9 itself (FUN_1009c450), no reply
  needed. Send others `02 0a S id` on 0x13: `02 0a 00 00 00 00 01 00 00 00 01 00 00 00 33`.
- Hero menu back: `player->exitCasino` (FUN_1009c350) sends `00 0a` first if matchmaking, then CASINO_EXIT
  `00 0b 00 00 00 00` on 0x13. Reply `01 0b 00 00 00 00 00` on 0x13 (state 7, removes self, unregisters 0x13; the
  casino stays in the client's list). Others: `02 0b S id` (`02 0b 00 00 00 00 01 00 00 00 01 00 00 00 33`,
  counter -1) plus `02 0a S id` if the leaver was listed.
- Casino empty or started: to friends on 0x11, FRIENDLY_CASINO_LEFT `02 16 S subject CI S name`:
  `02 16 00 00 00 00 01 00 00 00 01 00 00 00 32 02 e9 03 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65 00 00 00 00 05 00 00 00 05 00 00 00 61 6c 69 63 65`
  Client case 0x16: finds the casino by trailing name; removes it and its menu entry (+0x28 -> FUN_100d9000) only
  if the local player is **not** in it (casino vt+0x10 FUN_1009ad20).
- Joining a closed or unknown casino id: CASINO_NOT_FOUND on **0x11** `01 25 RB(value = id)`:
  `01 25 00 e9 03 00 00`. Case 0x25: if that casino is type 2, removes the local player and the casino,
  unregisters 0x13; always `player->+0x98(0)`, state 4 (LOGGED_IN). Inferred: the hero menu then waits for state 9
  forever; the user must back out.
- FRIENDLY_CASINO_UNAVAIL `01 18 RB` (0x11): listeners +0x20 -> arena FUN_100d8480 sets arena+0x1c = 1 (UI
  meaning not traced).
- After the battle, EndArenaState re-logs into CasinoSystem; the stale friendly casino is dropped by the next
  zero FRIENDLY_UPDATE or F_CASINO.
