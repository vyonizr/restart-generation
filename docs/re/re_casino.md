# CasinoSystem protocol (Reset Generation native DLL) — RE notes

Source: `ResetGeneration-Win32-Web.dll` (image base 0x10000000). All addresses are VAs in that DLL.
"Observed" = read directly from decompile/disassembly. "Inferred" = my reasoning, not proven.
Helper scripts used: `SCRATCH\casino\fn.sh` (print decompiled function), `callers.sh`, `dis.sh`, `find.js` (find dword in image).

## 00. LOGIN reply — byte-exact (answers the live-capture question)

The captured request `00 00 | 01 00 00 00 | 01 00 00 00 19 00 00 00 19 00 00 00 "Reset Generation v. 1.1.3"` matches §4 exactly: header kind 0 / action 0, `u32 1`, then a String whose first u32 (`1`) is the sender's string header word (refcount 1, encoding bits 28..30 = 0).

The client expects RESPONSE kind 1, action 0 on MT type 0x11. Body (146 bytes, generated by `SCRATCH\casino\mk.js`):

Success / failure fields:
- There is no success field. `FUN_10047460` case 0 never reads `result`; receiving this message means success. Parser: `FUN_100979e0` (verified in disassembly 10097A86..10097AC0: profile, then u8 flag, then CasinoInfo only if flag != 0).
- `hasCasino` must be 1 with a valid CasinoInfo the first time. With 0, the handler finds no current casino (`main->vt+0x1c` = main+8 is NULL), builds a casino object from a NULL info (`FUN_10097be0` calls `info->vt+0x10`) and crashes (inferred from the code path).
- CasinoInfo `type` must be 1 (PUBLIC) so it becomes the ranked casino (`FUN_10094b60`); type 0 makes the factory return NULL (`FUN_10048e70`).
- Profile key `id` must be a decimal string; the client uses it to recognise itself in later lists. Keep `name` equal to the name sent in the type-3 message. Don't send `type=REMOTE` for this player (the map is merged into the local profile, `FUN_100495a0`).
- To reject a version, send RESPONSE VERSION_NOT_SUPPORTED instead: `01 22 00 00 00 00 00`. The login menu then shows an error (`FUN_100c54d0`).

What happens next (client side):
1. Player state goes LOGGING_IN (3) -> LOGGED_IN (4) (`FUN_10049070` -> `FUN_100972f0`).
2. Login-menu listener `FUN_100c6380` leaves "Connecting..." and opens the arena menu (`FUN_100c5ec0` -> `FUN_100d9040`); if app+0x84 is set it first waits 7.5 s.
3. The login-menu tick sends `00 05 00 00 00 00` GET_STATISTICS once it sees state 4 (`FUN_100c5fd0` -> `FUN_10046500`). It can be skipped if the menu switches first. Reply `01 05 RB StatsRecord` (§4).
4. The client does **not** send CASINOSYSTEM_UPDATE or a casino-list request after login. The public casino comes only from the LOGIN reply. Further traffic is user-driven: GLOBAL_RANKED_GAME -> CASINO_ENTER on MT type **0x12**; LINK:RANKINGS -> GET_RANKINGS; CREATE_FRIENDLY_ARENA -> CASINO_CREATE; FRIENDLY_UPDATE polling only when friendly casinos exist. Achievements upload (GET_ACHIEVEMENTS request) comes from `FUN_10046750`; its trigger was not traced.

## 0. TL;DR for the server author

1. CasinoSystem messages are carried on the NAF "connection" session as **message type 0x11** (decimal 17).
   Casino-specific traffic uses **type 0x12** (PUBLIC/ranked casino) or **type 0x13** (FRIENDLY casino).
   Table (seat) traffic uses **type 0x15** on a *second* session opened to the address given in CASINO_MATCHED_UP.
   The join-room key/value message goes out as **type 3 (MT_GAMESERVER)**.
2. Every CasinoSystem message starts with a 2-byte header: `[kind u8][action u8]`, kind 0=REQUEST, 1=RESPONSE, 2=EVENT.
3. All integers are little-endian (packet streams are created with ios flags = 1: binary, no byte-swap bit 4).
4. Strings are the engine's internal string object: `u32 flags, u32 len, u32 len, len bytes` (no NUL). See §2.2.
5. The client sends nothing until the *session* reports "connected" (`FUN_10047fc0`). That callback sends, in order:
   (a) a type-3 MT_GAMESERVER key/value message with `name=<player name>` and `roomname=CasinoSystem`,
   (b) REQUEST CASINOSYSTEM_LOGIN (type 0x11). So if no packet is seen, the transport-level session connect is not completing; this is not a casino-layer issue (see §1).
6. To leave "Connecting..." the server must answer LOGIN with RESPONSE CASINOSYSTEM_LOGIN containing the player profile and a PUBLIC casino descriptor. The client then goes to LOGGED_IN and opens the arena menu.

## 2. Primitive encodings

### 2.1 Integers
- `u8`: 1 byte. `u16`/`u32`/`i32`: little-endian. Writers: `FUN_100f45f0` (u8), `FUN_100f4440` (u16), `FUN_100f4340` (u32), `FUN_100f4240` (i32), `FUN_100f46c0` (bool, 1 byte).

### 2.2 String (`FUN_100efee0` write, `FUN_100f0000` read, size `FUN_100ef110` = 12 + bytes)
```
u32 flags   ; bits 28..30 = encoding (0 = 8-bit, 1 = 8-bit with hidden length prefix, 2 = UTF-16LE). Low 28 bits = sender's refcount (garbage, ignored by reader).
u32 length  ; characters; stored as the string length
u32 count   ; characters; reader uses THIS one * (enc==2 ? 2 : 1) as the raw byte count
bytes[count * width]   ; no terminator
```
Server should send `flags=0, length=n, count=n, n ASCII bytes`. Reader fails if encoding > 2 (`FUN_100f0000` @100F008A).

### 2.3 Header (base class vtable `10182298`)
`[kind u8][action u8]`, written as one LE u16 = kind | action<<8 (`FUN_100994b0`, read `FUN_10099490`, ctor `FUN_10099be0(this, kind, action)`). Size 2 (`FUN_100994d0`).

### 2.5 Profile (player property map, vtable `1017b118`)
Write `FUN_10049710`, read `FUN_10049340`, size `FUN_10049870`.
```
u32 count
count * { String key, String value }
```
Keys seen: `id` (decimal player id; the client uses it to recognise itself, `FUN_10047240`), `name` (`FUN_100472c0`), `fame` (decimal), `type` (`LOCAL`/`REMOTE`, `FUN_100494f0`, `FUN_100ce050`), `heroType`, `random` (used for matchmaking, `FUN_10097dc0`).
The LOGIN response profile is merged into the local player's map, overwriting keys (`FUN_10049ba0` -> `FUN_100495a0`). Inferred: do not send `type=REMOTE` for the local player.

## 5. Client state machine

### 5.1 Player states (player +8, toString `FUN_1009bbc0`, vtable `1017b020`)
0 INIT, 1 INITED, 2 LOGGED_OUT, 3 LOGGING_IN, 4 LOGGED_IN, 5 LOGGING_OUT, 6 INIT, 7 EXITED_CASINO, 8 ENTERING_CASINO, 9 ENTERED_CASINO, 10 EXITING_CASINO, 11 RESERVING_SEAT (= matchmaking requested), 12 SEAT_RESERVED, 13 BEING_SEATED, 14 UNSEATED, 15 SEATED, 16 BEING_UNSEATED.

Player methods (vtable `1017b020`): `+0x10` login (`FUN_10097090`: state 3, `casinoSystem->connect(player,1)`), `+0x4c` enterCasino (`FUN_1009b9b0`: state 8, `casino->enter`), `+0x50` exitCasino (`FUN_1009c350`), `+0x54` startMatchmaking (`FUN_1009c3c0`: needs state 9, state 11), `+0x58` leaveSeat (`FUN_1009c410`), `+0x5c` cancelMatchmaking (`FUN_1009c450`), `+0x60` enteredCasino (state 9), `+0x64` beginSeating (`FUN_10049090`: state 13, `table->connect`), `+0x68` exitedCasino (7), `+0x6c` seatReserved (12), `+0x74` seated (15), `+0x78` unseated, `+0x7c` expired (14).

### 5.2 CasinoSystem client (object at app slot 0x3a, ctor `FUN_10047050`, vtable `1017af90`)
Connection state at +0x18 via `FUN_1010ef00`: 1 = connecting (`FUN_10047340`), 2 = connected (`FUN_10047fc0`), 3 = disconnected (`FUN_100482c0`).

### 5.3 Login / "Connecting..." (login menu `FUN_100c5fd0` tick, `FUN_100c5ab0` draw)
1. The SNAP/NAF login object (menu+0x2c) reaches a logged-in state; the menu calls `player->login(casinoSystem)` (`FUN_100c5fd0`).
2. `FUN_10047340` -> `FUN_10110ec0` -> `FUN_10046d10`: create session to the static `naf://.../CasinoSystem` address, register 0x11, `connect(80000)`.
3. Transport reports connected -> `FUN_10047fc0`: send MT_GAMESERVER `{name, roomname=CasinoSystem}` (type 3) and LOGIN (type 0x11).
4. Server sends LOGIN response -> player LOGGED_IN -> player listener `FUN_100c6380` -> `FUN_100c5ec0` opens the arena menu (`FUN_100d9040`). The tick also sends GET_STATISTICS once state == 4 (`FUN_100c5fd0` -> `FUN_10046500`).
The dialog text in `FUN_100c5ab0` depends on the SNAP login object state: 3 -> `LOGIN_LOGGING_IN`, 1 -> `CANCEL_LOGIN`, other -> `LOGIN_CONNECTING`. "Connecting..." stays until step 4. Errors: VERSION_NOT_SUPPORTED -> listener `FUN_100c54d0` sets error flags; casino disconnect -> `+0xc(0)`.

### 5.4 Ranked (GLOBAL_RANKED_GAME) happy path
1. Arena menu tick `FUN_100d8700`: if player state is 4 or 7, take the PUBLIC casino (`main->vt+0x1c` = main+8) and call `player->enterCasino` -> CASINO_ENTER req `00 08 u32 id` on **0x12**. (The casino handler for 0x12 is registered just before, `FUN_10097ff0`.)
2. Server: RESPONSE CASINO_ENTER on 0x12 -> state 9. Matchmaking menu (`FUN_100e33a0`; it calls `player->+0x54`, seen in `FUN_100e3670`) sends CASINO_MATCHMAKING `00 09 S heroType S random` -> state 11. RESPONSE MATCHMAKING is optional (listener only).
3. Server: EVENT CASINO_MATCHED_UP on 0x12 with a TableDescriptor -> client disconnects the CasinoSystem session (`[esi+2Ch]->+0x5c` @100983F5), state 12 then 13, opens a new session to `TD.server`, registers type 0x15, `connect(1800000)`.
4. Table session connected (`FUN_100cded0` sets a flag) -> table tick `FUN_100ce4c0` -> `FUN_100ce340`: sends MT_GAMESERVER join `{name, id, roomname=TD.name}` (type 3) and SEAT_TAKE `00 0d u32 playerId` (type 0x15).
5. Server: RESPONSE SEAT_TAKE -> state 15 SEATED. Game start is not driven by a casino message (see §6).
Failure paths: MATCHMAKING_FAILED dialog (`FUN_100eb070`/`FUN_100eb170`), GAME_START_FAILED request, SEAT_RESERVATION_EXPIRED.

### 5.5 Friendly casinos
- Create: CREATE_FRIENDLY_ARENA (only if the friends list is not empty, `FUN_100d8aa0`) -> CASINO_CREATE `00 14 u32 0` (0x11) -> RESPONSE `01 14 RB CI(type 2)` -> casino added (channel 0x13).
- List: GET_FRIENDLY_CASINO_LIST `00 07` (0x11). Inferred: server replies RESPONSE **0x03** F_CASINO (`01 03 RB u8 n n*CI`) because response 7 is ignored and response 3 carries the list.
- Status poll: FRIENDLY_UPDATE `00 19 u32 casinoId` per casino (`FUN_10048120`, from `FUN_100d85b0`) -> RESPONSE `01 19 RB u32 id u32 inLobby u32 waiting u32 playing`.
- Join: JOIN_FRIENDLY_ARENA / `FRIEND_<id>` -> `FUN_100d8940` -> `player->enterCasino(casino)` -> CASINO_ENTER on **0x13**.
- Start: host sends FRIENDLY_CASINO_START `00 1c u32 casinoId` (0x11). Inferred: server then sends CASINO_MATCHED_UP on 0x13 to each member, and the table flow of §5.4 step 3 follows.
- Friend notifications: EVENT FRIENDLY_CASINO_ENTERED/LEFT (0x11).
- Friends: REGISTER_FRIENDS (`FUN_10046e90`, caller @10096B2D), FRIEND_ADD/REMOVE (`FUN_10046f20`/`FUN_10046fb0`).

### 5.6 Rankings / statistics / achievements
- LINK:RANKINGS -> GET_RANKINGS `00 04 u32 0` -> RESPONSE with 3 StatsRecord lists (top 10, friends, near you). The UI shows FRIENDS_RANKING only if the friends list has more than 1 entry, and NEAR_YOU only if it is not empty (`FUN_100d93e0`).
- GET_STATISTICS sent automatically after login -> RESPONSE `01 05 RB SR` (YOUR_STATS).
- Achievements: `FUN_10046c80` (from @1004677F) uploads local counters in GET_ACHIEVEMENTS request; RESPONSE returns 200 bytes.

## 6. In-match traffic (question 4)

Observed:
- After MATCHED_UP the client leaves the CasinoSystem session and opens a **separate NAF session to `TD.server`** (`FUN_100cdd00`). On that session it registers only type 0x15 for casino-layer traffic and sends an MT_GAMESERVER (type 3) join with `roomname = TD.name` (`FUN_100ce340`).
- The table object (`FUN_100cdf10`, vtable `10187dd0`) tracks reserved (+0x14) and seated (+0x10) players and `TD.nplrs`.

Inferred (not proven, needs the transport agent):
- `TD.name` is the game-room name on the game server and `TD.server` is a naf:// address whose service part maps to a SNAP game room (compare `FUN_10003760` building `naf://%s:%u/CasinoSystem` with the Java side joining room "CasinoSystem"). A replacement server can probably point `TD.server` at itself with a per-table room name.
- Gameplay packets go through that game room (MT_GAMEROOM / MT_USER), relayed by the server between room members. The room has a "hosted" property (`FUN_1010fd80`, `FUN_10110210`) and MT_HOSTMIGRATION exists, so one client is probably the host (likely the first to join or the one marked "hosted"). UI strings CONNECTION_TO_HOST_LOST / PLAYER_HAS_DISCONNECTED / WAITING_FOR_PLAYERS support a host/peer model.

## 7. Minimal server script (inferred from the above)
1. Let the client connect to the "CasinoSystem" room; make sure the transport reports the session as connected.
2. Receive type 3 join (`name`, `roomname=CasinoSystem`) — acknowledge as the transport requires.
3. Receive type 0x11 `00 00 01000000 S"Reset Generation v. 1.1.3"`. Reply type 0x11:
   `01 00 | 00 | 00000000 | P{id=<n>, name=<snap user>, fame=0} | 01 | CI{type=1, id=1, 0, 0, 0, name="Global"}`.
4. Answer GET_STATISTICS with `01 05 00 00000000 SR{...}`; answer GET_RANKINGS, GET_FRIENDLY_CASINO_LIST (with F_CASINO n=0), REGISTER_FRIENDS (generic), GET_ACHIEVEMENTS (200 zero bytes).
5. On type 0x12 CASINO_ENTER reply type 0x12 `01 08 00 00000000 P{...} CI{public}`.
6. On type 0x12 CASINO_MATCHMAKING pair players; send each type 0x12 `02 1f S"<id>" TD{id, name, nplrs=0, maxplrs, skill, Address{0, 1, "naf://host:port/<table room>", 1}}`.
7. On the table session, on type 0x15 SEAT_TAKE reply type 0x15 `01 0d 00 00000000`.

6. Exact naf address string format for `TD.server` and how it maps to SNAP rooms; whether the casino session really must be dropped on MATCHED_UP (observed call to session `+0x5c` = `FUN_1011e100` disconnect).
7. Which messages the server should send for the friendly flow after FRIENDLY_CASINO_START (MATCHED_UP on 0x13 is inferred). Who calls table `+0x2c` (SEAT_RESERVE) was not found; in the ranked flow the client never sends SEAT_RESERVE, only SEAT_TAKE.
