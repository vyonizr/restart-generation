# Bots run with retuned AI profiles

Bots play at the engine's own strength (ADR 0008), and that proved too easy: the engine AI is a greedy, one-move-ahead scorer with no lookahead, so a skilled player beats it with no risk. The engine has no difficulty setting. Its strength comes from six situational AI profiles, plain integer weights in `data/gameplay/ai/AIS*.xml` inside `gameplay.pak`. The server retunes the four working profiles (`AISD`, `AISGTP`, `AISGH`, `AISROP`) for the Bots' engines only. A committed deltas file lists `profile / key / value` triples. At start the server applies them to the XML read from the player's own `gameplay.pak`, rebuilds the pak in memory, and gives it to each Bot's engine before boot. The engine reads each profile once per process, so the override must be in place before the first AI player is built. `AISMT` (mind-tricked) and `AISF` (frogged) stay stock because their behavior is deliberate. People's engines never see the change.

This is a second kind of in-memory change beside the patches of ADR 0007: replaced data instead of replaced code. ADR 0007 forbids file changes in the player's game copy, in browser storage and on disk. The Bot's pak exists only in the server process's memory, and the original stays untouched.

## Considered options

- **Load the `Agressive/` profiles in the game's data.** Rejected: they are a stale snapshot from before special skills, threat fields and movement-cost distances existed. They lack about 75 of the live keys, which would load as 0, and use tile-based distance thresholds (3 and 7) where the live files use movement cost (1200 and 2100). The engine never loads them, and no mission sets the `AIType` that would select them.
- **Raise the AI's think budget.** Rejected: the budget only paces how many board cells the analysis handles per tick. It changes how fast the AI decides, not how well, and it is already at its cap on the virtual clock.
- **Choose moves on the server.** Rejected: it duplicates the game rules outside the engine, and the server only relays battles (ADR 0005).
- **Add lookahead inside the engine.** Deferred, not rejected. It is the only change that fixes short-term-only play, but it means reverse engineering and patching the scorer. It is worth doing only if weight tuning plateaus below the target.
- **A human playtest in the gate.** Rejected: the maintainer doesn't measure strength by hand, so the gate is automated. Players' opinions come afterwards and feed the next change.
- **Weight changes picked by reading the profiles.** Tried, and nothing beat the stock Bot (see Consequences). Moderate weight changes sit inside the noise of a 24-battle comparison.
- **Commit modified copies of the XML files.** Rejected by ADR 0001: players bring their own game files. Deltas applied to the player's own copy keep game data out of the repo.

## Consequences

- The gate is automated self-play, `tools/selfplay.mjs` (`npm run selfplay`): a candidate set of changes against a base over many headless battles, each Bot's engine reading its own result from the engine's rank table, the two engines required to agree. The harness itself was checked: the same profiles on both sides won 16 of 30 (53%), and a deliberately crippled candidate (every random term at 10000) won 1 of 12. It runs three battles at once at 8 times real time, about 2 battles a minute, and needs about 1 GB per battle. It and `tools/tune.mjs` run at low priority.
- Self-play is noisy: 24 to 40 battles leave a standard error of 8 to 10 percentage points, so only large effects show, and it shows "stronger than stock", not "stronger than a top player". There is no population to rank a Bot against ("top 3 on the ranking" can't be measured), so no claim of that kind is made.
- Measured results: none of the first five changes beat the Bot running the best set so far (14, 13, 13, 12 and 11 wins of 24: calmer randomness, defend the castle, defend the princess, go for the laser cannon, fix the `AISGTP` typo). All eleven candidate changes stacked won 13 of 30 against stock; zeroing every random term won 17 of 40; weighting the objective more won 14 of 30. The profiles are robust to moderate changes. By the plateau rule, further weight tuning is not the next step: a stronger Bot needs lookahead (the deferred option above), which is a new decision and ticket.
- Hero choice is the one lever with a signal. Over 286 decided battles between equal Bots, AGGRESSOR won 67% of its battles (36 of 54), CYBORG 57% and HEDGEHOG 56%; NINJA won 39%. Only AGGRESSOR is clearly above 50%, so the signal is weak.
- Bots don't cheat: no hidden information, no bonus resources.
- A delta whose key is missing from the player's XML fails at server start, which catches a game-version mismatch.
- The server needs a pak writer. `tools/re/pakx.js` only extracts.
- Two difficulties (CONTEXT.md "Difficulty"), chosen per match by the player who presses Start. **CPU** is the game's own AI profiles with a random hero, as before. **Expert** runs the deltas in `server/bot-ai.json` (none yet) and draws its hero from `server/bot-heroes.json` (AGGRESSOR, CYBORG, HEDGEHOG). With none of the weight changes shown to help, Expert is the strongest-looking hero pool on stock profiles, and the page says only that: "Expert CPU players choose from the strongest heroes". It is not shown to be harder.
- The page asks when a friendly Start has bots: with 2 or 3 people listed, No, CPU or Expert; for a player alone, CPU or Expert (command 900's P1 is 1 for CPU, 2 for Expert; command 901 answers `ask`, `level`, `go` or `gone`). An older page that doesn't ask gets CPU bots.
